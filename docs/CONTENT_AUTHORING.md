# Examiner onboarding and authoring

Examiner responsive web only. Individual/institute is one account at launch. Applicant provides photo/bio/exams/subjects/experience/links, ten sample questions for one exam, manual KYC documents and versioned agreement acceptance. Samples enter ordinary QC. Ops approves/rejects with reason; accepted examiner starts tier New. KYC verification and sample approval are distinct gates; no real sales/payout before required checks.

## Editor

Choose exam/stage/type/template; show section counts, timing and marking. Content is plain text with KaTeX math and pipe tables (DECISIONS Q1-Q3); images attach as scanned assets. The editor preview renders English and Hindi with the shared parser, and the server rejects malformed math, blocked KaTeX commands and ragged tables with field-level errors (import: exact cell, code `INVALID_CONTENT`). English required; bilingual test requires English/Hindi stem, options, passage and solution. Stable option IDs separate answer identity from display order. Tag from admin syllabus and examiner-set difficulty. Store source provenance for PYQs. Preview exact student rendering before submit.

Hindi is all-or-none per question: a question with any Hindi needs Hindi in the stem, all four options and the solution, and a grouped question with Hindi needs a Hindi passage. Samples, drafts and import rows enforce this with field- or cell-level errors. Question type is derived on the server (comprehension when a passage is attached, otherwise single-choice); PYQ year and shift are dropped when the question is not a PYQ. Edits must send the version they were based on; attached images and passages must belong to the examiner.

Draft save uses expected revision and clear saved/saving/conflict/error states. Server sanitizes allowed nodes/HTML and forbids scripts, remote embeds and executable links. Shared passages are versioned. Reuse own approved questions by reference; warn/block paid reuse per QC. Exam template and price tier selection are validated server-side. Scheduled publication is MVP; competitive live windows are Phase 2.

## Excel contract

One `Questions` sheet; columns: row_id, section, position, group_id, stem_en, stem_hi, option_a_en through option_d_en, option_a_hi through option_d_hi, correct_option, solution_en, solution_hi, subject_code, topic_code, difficulty, source, pyq_year, image_refs. The current schema has no stable subject/topic code columns, so `subject_code` and `topic_code` currently contain the corresponding UUIDs. Template version is selected in the UI and validated server-side. Number of options follows the template; if not four, version the template contract explicitly. `Groups` sheet maps group_id to English/Hindi passage and image references.

Preserve LaTeX as plain text; images refer to safe relative filenames in supplied ZIP. No OCR, macros, formula execution or implicit external network references. Reject zip traversal, symlinks, duplicate names, unsupported MIME, decompression bombs and oversized batches; proposed starting limits 200 questions/20MB compressed/100MB expanded, verified in S2/M3.

Workflow: upload -> parse/validate preview -> row/column errors -> user fixes source -> commit accepted manifest atomically. No silent partial import. File+manifest digest and idempotency key prevent duplicate commit. Report unsupported formatting rather than destroying it. A 100-question synthetic bilingual import with group/images/math must require zero manual fixes; invalid fixture must point to exact rows/cells. Admin PYQ ingestion uses same parser with official year/shift/provenance fields and coverage register.

The current M3 import implementation handles four-option question rows and validates the selected published template, section, position and examiner taxonomy. An optional `Groups` sheet maps `group_id` to English/Hindi passages and image references; question-level `image_refs` attach images to questions. ZIP image paths must be safe relative paths and use JPEG, PNG or WebP (10 MB per image maximum); images are malware-scanned and stored under server-only keys before the preview can be accepted. A clean archive scan does not replace scanning each referenced image. The API rejects formulas, unsafe/duplicate ZIP entries, macros, external links and invalid group/image references with row-specific errors. A synthetic 100-question bilingual parser case is covered, but the complete browser upload and preview-to-commit journey has not been validated in a browser.

In local/test, the only application agreement is a clearly marked non-legal placeholder. Deployed APIs must receive owner-approved `EXAMINER_AGREEMENT_VERSION` and `EXAMINER_AGREEMENT_TEXT`; startup fails if either is missing. Asset completion verifies bytes, declared MIME and SHA-256, scans with ClamAV, and copies clean bytes to a server-only object key so an unexpired upload URL cannot replace the accepted file. Scanner failures fail closed. Ops admins can request a five-minute, audited attachment download for clean KYC files; a clean scan does not verify the document or applicant. KYC requirements, the verification decision, retention period and sales/payout gate still require owner/legal approval.

## Examiner operations

Dashboard: sales/attempts/revenue by test/day, payout statements, uploaded quarterly TDS certificates, tier inputs (QC pass rate, duplicate rejections, key corrections, report response time), coupon attribution. Admin sets tier monthly and allowed prices/fast review lane. Ratings and detailed examiner question statistics remain Phase 2.
